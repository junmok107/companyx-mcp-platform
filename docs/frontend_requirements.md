# 프론트엔드 기능 요구사항

> 이 문서는 **기능 요구사항만** 정의한다. 화면 레이아웃, 컴포넌트 구조, 색상/타이포그래피 등
> 디자인·UI/UX 관련 결정은 포함하지 않으며, 전적으로 디자인 담당(Claude Design)의 재량에 맡긴다.

## 1. 프로젝트 개요

MCP(Model Context Protocol) 기반 통합 지능형 데이터 검색 플랫폼의 웹 프론트엔드다.
백엔드는 PostgreSQL(정형 데이터), 지식 그래프(networkx), pgvector 벡터 검색 세 가지 도구를
갖추고 있으며, 사용자가 자연어로 질문하면 규칙 기반 라우터가 적절한 도구를 자동 선택해
호출한다. 프론트엔드는 이 백엔드 기능을 사람이 쓸 수 있는 형태로 노출하는 것이 목적이다.

전체 인터페이스는 한국어 기준이다 (질문·답변·데이터 전부 한국어).

## 2. 연동 대상 — 백엔드가 제공하는 기능

백엔드는 MCP 서버(`mcp_server/server.py`)로 다음 4개의 도구(tool)를 노출한다.
프론트엔드는 이 4개 도구를 호출할 수 있어야 한다 (전송 방식/API 계층 구현은 프론트엔드
요구사항 범위 밖이며, 이 문서는 "무엇을 호출할 수 있어야 하는가"만 규정한다).

| 도구 | 설명 | 처리 대상 |
|---|---|---|
| `ask` | 도구를 자동으로 고르는 진입점 (권장 기본 경로) | 질문 유형 불문 |
| `nl2sql_query` | 정형 데이터 질의 (매출, 계약, 직원, 제품, 티켓 등 수치/집계) | 표 형태 데이터 |
| `knowledge_graph_query` | 개체 간 관계 질의 (담당, 소속, 사용, 리드 등) | 그래프 노드/관계 |
| `vector_search_query` | 비정형 문서 의미 검색 (장애보고서, 기술문서, 회의록, 제안서) | 문서 청크 |

각 도구는 입력으로 자연어 질문 문자열 하나만 받는다.

### 2.1 공통 응답 형식

네 도구 모두 동일한 최소 형태로 응답한다.

| 필드 | 타입 | 내용 |
|---|---|---|
| `answer` | string | 사용자에게 보여줄 자연어 답변 (실패/거부 시에도 항상 채워짐) |
| `raw_data` | object \| null | 도구가 실제로 조회한 원자료. **쿼리 자체를 실행하지 못한 경우에만** `null` (아래 §2.3 참고) |
| `tool` | string | 응답을 생성한 도구 이름 (`nl2sql` \| `knowledge_graph` \| `vector_search`) |
| `source` | array | 근거 목록. 비어 있을 수 있음 |

`ask`는 위에 더해 `routed_to`(실제로 라우팅된 도구 이름)를 함께 반환한다.

### 2.2 도구별 추가 필드 및 `raw_data` 형태

- **NL2SQL**
  - 추가 필드: `sql` (실행/시도된 SQL 문자열). `error`는 SQL이 DB에서 실행 중 오류가 난
    경우에만 추가로 붙는다 — SQL 검증 자체가 거부된 경우(안전하지 않은 쿼리)는 `sql`만
    있고 `error`는 없다.
  - `raw_data`: `{ columns: string[], rows: any[][], row_count: number, total_count: number | null, truncated: boolean }`
  - `source`: 실행된 SQL 문자열 1개를 담은 배열
  - `total_count`가 `null`일 수 있다 (결과가 상한을 넘겼는데 정확한 총계 계산에 실패한 경우)
  - `truncated: true`면 표시된 행이 전체 결과의 일부라는 뜻 (기본 상한 200행)

- **지식 그래프**
  - 추가 필드: `spec` (질문을 해석한 탐색 스펙, 디버깅/투명성 용도)
  - `raw_data`: `{ nodes: object[] }` — 각 노드는 `id`, `type`, `name` 및 노드 타입별 속성 포함, 집계 모드에서는 `count` 포함
  - `source`: 근거로 쓰인 노드 id 배열 (사람이 읽는 이름이 아님 — 사람이 읽을 이름은 `raw_data.nodes[].name`에 있음)

- **벡터 검색**
  - `raw_data`: 검색된 문서 청크 목록. 각 항목은 다음 필드를 갖는다.
    - `doc_id`: 문서 id (예: `DOC-015`)
    - `chunk_index`: 문서 내 청크 순번
    - `content`: 청크 본문 텍스트
    - `metadata.type`: 문서 유형 (`incident_report` / `technical_doc` / `meeting_note` / `proposal`)
    - `metadata.title`: 문서 제목
    - `similarity`: 질의-청크 코사인 유사도 (0~1)
    - `rerank_score`: 재순위 후 최종 점수
    - 이 목록은 **실제 답변에 인용된 근거뿐 아니라, 검색은 됐지만 최종 답변에는 반영되지 않은
      후보 청크까지 포함**한다 (근거인지 여부는 `source`에 doc_id가 있는지로 판단해야 한다)
  - `source`: 근거로 쓰인 문서 id 배열. `raw_data`에 포함된 문서 중 실제로 답변에 반영된
    것만 추린 부분집합이다

### 2.3 거부/오류 응답

아래 세 부류 모두 결과적으로 `raw_data: null`, `source: []`, `answer`에 오류 설명 텍스트가
담기는 형태로 온다. 다만 도구별 부가 필드(`sql` 등) 포함 여부는 부류마다 다르다 (아래
"부가 필드" 관련 주의 참고).

- **사전 거부** (도구를 아예 실행하지 않음 — 부가 필드 없음)
  - 질문이 빈 문자열이거나 공백만 있음
  - 질문이 2,000자를 초과함
- **도구가 스스로 인지하고 정중히 처리한 실행 실패** (도구는 실행을 시도했고, 실패를
  도구 내부에서 잡아 친절한 한국어 오류 문장으로 바꿔 반환함 — 도구별 부가 필드가 함께
  붙을 수 있음)
  - 예: NL2SQL의 SQL 검증 거부(안전하지 않은 쿼리), NL2SQL의 DB 실행 오류, 지식 그래프의
    스펙 추출 실패
- **도구도 처리하지 못한 예외** (도구 자체의 오류 처리로도 못 잡은 예외가 서버
  최상위에서 잡힘 — 흔치 않은 경로. 부가 필드 없음. `"처리 중 오류가 발생했습니다:
  <예외타입>: <메시지>"` 형태의 일반화된 텍스트가 `answer`에 담긴다)

이 경우도 항상 §2.1의 공통 형식을 따르므로, 프론트엔드는 별도의 "에러 응답 스키마"를
따로 만들 필요가 없다.

**주의 — `raw_data == null`을 "결과 없음/실패"의 판정 기준으로 쓰지 않는다.** `raw_data`가
`null`인 경우는 위 세 부류처럼 **쿼리가 실제 데이터를 조회하는 단계까지 가지 못했을 때뿐**
이다. 쿼리(또는 그래프 탐색·문서 검색)가 정상적으로 끝까지 실행됐지만 "찾는 정보가 없다"는
경우는 오히려 `raw_data`가 채워진 채로 온다.
- 지식 그래프: 개체를 못 찾거나 지원하지 않는 관계면 `raw_data`가 `{"error": "...", "nodes": []}`
  형태의 dict로 채워진다 (`null`이 아님).
- 벡터 검색: 관련 문서를 못 찾아 "관련 문서를 찾지 못했습니다"라고 답할 때도 `raw_data`에는
  검색·재순위를 마친 후보 청크 목록이 그대로 들어있다 (`source`만 빈 배열이 됨).
- NL2SQL: 조회 결과가 0행이어도(`"조회된 결과가 없습니다"`) `raw_data`는
  `{columns, rows: [], row_count: 0, ...}`로 채워져 있다.

따라서 "결과 없음" 상태를 감지하려면 `raw_data`의 존재 여부가 아니라 도구별로 `source`가
비어 있는지, `raw_data.error`가 있는지, `raw_data.nodes`/`raw_data.rows`가 비어 있는지를
확인해야 한다.

**주의 — 부가 필드(`sql`, `spec`, `routed_to`)는 항상 존재하지 않는다.** 입력 검증 단계
(빈 질문·길이 초과)에서 거부되면 이 필드들은 키 자체가 응답에 없다. 도구가 실제로 실행을
시도한 뒤 실패한 경우(예: NL2SQL의 SQL 검증 실패, DB 오류)에만 `sql`이 포함되는 식이다.
프론트엔드는 이 필드들의 존재 여부를 먼저 확인한 뒤 접근해야 한다.

**주의 — `answer` 필드가 항상 다듬어진 문장이라고 가정하지 않는다.** 대부분의 경우
`answer`는 사람이 읽기 좋은 한국어 문장이지만, 도구가 예상 밖의 내부 상태(예: LLM이
불완전한 중간 데이터를 생성한 경우)를 만나면 `"처리 중 오류가 발생했습니다: KeyError: ..."`
같은 원시 예외 텍스트가 그대로 담길 수 있다. 프론트엔드는 `answer`를 이런 경우에도 깨지지
않고 일반 텍스트로 표시할 수 있어야 한다 (문장 구조를 전제로 한 파싱/가공을 하지 않는다).

## 3. 기능 요구사항

### 3.1 질문 입력 및 실행
- 사용자가 자유 형식의 한국어 자연어 질문을 입력하고 제출할 수 있어야 한다.
- 입력 길이 제한(2,000자)을 사용자가 인지할 수 있어야 한다 (초과 시 백엔드가 거부하지만,
  제출 전에 사용자가 인지하도록 하는 것이 바람직하다).
- 빈 질문은 제출할 수 없거나, 제출 시 백엔드의 거부 응답을 그대로 노출해야 한다.
- 기본 경로는 `ask` (자동 라우팅)여야 한다.
- 사용자가 원하면 특정 도구(NL2SQL / 지식 그래프 / 벡터 검색)를 직접 지정해 질의할 수
  있어야 한다 (해당 도구의 개별 엔드포인트 호출).

### 3.2 응답 표시
- `answer` 텍스트는 항상 표시되어야 한다 (성공/실패 무관하게 항상 존재하는 필드).
- 어떤 도구가 답변을 생성했는지(`tool`, `ask` 사용 시 `routed_to`)를 사용자가 확인할 수
  있어야 한다.
- **근거(`source`)를 확인할 수 있어야 한다.** 이 시스템의 핵심 가치는 "근거 없는 답변을
  지어내지 않는다"이므로, 답변이 어떤 데이터에 근거했는지 추적 가능해야 한다.
  - NL2SQL: 실행된 SQL 문
  - 지식 그래프: 근거 노드(사람이 읽을 이름으로 `raw_data`와 연결해 표시)
  - 벡터 검색: 근거 문서
- 도구가 실제로 조회한 원자료(`raw_data`)를 확인할 수 있어야 한다. 세 도구의 `raw_data`
  구조가 서로 다르므로(표/그래프 노드 목록/문서 청크) 각각을 사람이 읽을 수 있는 형태로
  표시해야 한다.
- NL2SQL 결과가 `truncated: true`인 경우, 전체 중 일부만 보여주고 있다는 사실과
  (가능하면) 전체 건수(`total_count`)를 사용자가 알 수 있어야 한다. `total_count`가
  `null`이면 "정확한 총계를 알 수 없음"으로 처리해야 한다 (0이나 임의 값으로 대체 금지).
- 지식 그래프 결과가 빈 경우(`nodes: []`)와 "해당 개체/관계를 찾을 수 없음"(`raw_data.error`
  존재) 경우를 구분해 표시해야 한다.
- 답변이 매우 긴 목록형 데이터(예: 다수의 행, 다수의 노드)를 포함할 수 있으므로, 결과
  건수가 많은 경우도 다뤄야 한다.
- **`answer`의 목록 건수와 `raw_data`의 실제 건수가 다를 수 있다.** `answer`(자연어 답변)는
  목록형 결과를 최대 50건까지만 나열하고 나머지는 "외 N건"으로 요약하지만, `raw_data`는
  그보다 더 많은 항목을 담고 있을 수 있다 (NL2SQL은 최대 200행, 지식 그래프는 상한 없음).
  `raw_data`를 표/목록 형태로 별도 표시하는 화면은 `answer`에 적힌 건수만 믿지 말고
  `raw_data` 자체의 길이를 기준으로 다뤄야 한다.

### 3.3 상태 처리
- **로딩 상태**: 도구 호출은 수 초(아래 §4 참고) 걸릴 수 있으므로, 요청이 진행 중임을
  사용자가 인지할 수 있어야 한다.
- **거부/오류 상태**: §2.3에 정의된 거부 응답(빈 질문, 길이 초과, 내부 오류)을 사용자에게
  명확히 전달해야 한다. 이 경우도 `answer` 필드에 이미 사람이 읽을 문장이 들어있으므로
  그대로 노출하면 된다.
- **"정보 없음" 상태**: 벡터 검색이 코퍼스에 없는 주제를 물었을 때, 또는 지식 그래프가
  존재하지 않는 개체/관계를 물었을 때는 정직하게 "찾지 못했다"고 답하는 것이 이 시스템의
  설계 의도다. 이런 응답을 오류로 취급하지 말고 정상적인 결과 유형으로 표시해야 한다.
  이 상태는 §2.3에서 설명하듯 `raw_data`가 `null`이 아닌 채로 온다 — `raw_data == null`
  여부가 아니라 `source`가 비어 있는지 등으로 판정해야 한다.

### 3.4 질문 이력
- 같은 세션 내에서 이전에 한 질문과 그 답변을 다시 확인할 수 있어야 한다 (여러 번
  질문-답변을 주고받는 흐름을 전제로 한다).
- 영속적 저장(로그인/계정, DB 저장 등)은 요구하지 않는다 — 필요 여부는 판단에 맡긴다.

### 3.5 예시 질문 제공
- 사용자가 무엇을 물어볼 수 있는지 감을 잡을 수 있도록, 도구별 예시 질문을 제공해야 한다.
  `questions.json`에 도구별 10개씩 총 30개의 실제 예시 질문이 있다 (참고용 데이터 소스로
  사용 가능). 각 항목은 `{ q, tool, hint }` 구조다.
  - `q`: 예시 질문 텍스트 — 사용자에게 노출할 대상은 이것뿐이다.
  - `tool`: 정답 도구 이름 (검증용)
  - **`hint`는 채점을 위한 내부 구현 힌트(예상 SQL 조인/조건 등)이므로 사용자 화면에
    노출해서는 안 된다.**

## 4. 성능 관련 요구사항 (실측치, README 기준)

아래는 참고용 실측 지연 시간이다. 이 값 자체를 UI에 노출할 필요는 없지만, 프론트엔드는
**수 초 단위의 응답 지연이 일반적인 상황**을 전제로 설계되어야 한다 (스트리밍 응답이
아니라 완료 후 일괄 응답).

| 구간 | 중앙값 |
|---|---|
| 라우팅 판정 (규칙 경로) | 0.00ms |
| 라우팅 판정 (LLM 폴백 경로) | 약 2.8초 |
| NL2SQL 질의 (목록형) | 약 5초 |
| NL2SQL 질의 (단일값, LLM 문장화 포함) | 약 9초 |
| 지식 그래프 질의 (결과 2건 이상) | 약 4.7초 |
| 벡터 검색 질의 | 약 6초 |

지식 그래프는 "결과 2건 이상"인 경우만 실측되어 있다. NL2SQL과 동일한 구조로, 지식
그래프도 **결과가 정확히 1건일 때만 답변 문장을 LLM으로 생성**하므로, 이 경우의 체감
지연은 위 4.7초가 아니라 NL2SQL의 단일값 지연(약 9초)에 준할 가능성이 높다 (NL2SQL도
LLM 호출 1회가 추가되며 목록형 대비 지연이 5초→9초로 거의 두 배가 됐다). 결과 건수와
무관하게 로딩 상태를 일관되게 표시해야 하는 이유이기도 하다.

## 5. 비기능 요구사항

- **정직성/투명성 우선**: 답변에 근거가 없으면 없다고 표시하는 것이 정상 동작이다. 근거
  없는 답변을 그럴듯하게 포장하거나, 실패를 숨기는 방향의 처리는 하지 않는다.
- **알려진 한계에 대한 기대치**: 벡터 검색은 질문과 문서의 어휘가 전혀 겹치지 않는
  순수 패러프레이즈 질문 일부를 놓칠 수 있다 (README 실측: 4건 중 1건). 이는 "관련 문서를
  찾지 못했습니다"라는 정상적인 실패 응답으로 나타나며, 프론트엔드가 별도로 감지하거나
  복구할 필요는 없다 — 다만 이런 응답이 버그가 아니라 시스템의 알려진 동작이라는 점을
  참고한다.
- **언어**: 인터페이스 및 표시 콘텐츠는 한국어 기준.
- **오프라인/로컬 전제**: 백엔드는 로컬 오픈웨이트 LLM(Ollama)과 로컬 PostgreSQL만 사용한다.
  외부 상용 API 호출을 프론트엔드에서 추가할 필요는 없다.
- **인증**: 별도 사용자 인증/권한 체계에 대한 요구사항 없음 (필요 여부 판단은 맡긴다).

## 6. 범위 외 (Out of scope)

- 화면 레이아웃, 정보 구조(IA), 내비게이션 구조, 컴포넌트 설계
- 시각 디자인(색상, 타이포그래피, 아이콘, 브랜딩)
- 반응형/디바이스별 대응 전략의 구체적 방식
- 프론트엔드-백엔드 간 실제 통신 프로토콜/API 게이트웨이 구현 (현재 백엔드는 MCP
  stdio 프로토콜로만 노출되어 있으며, 웹에서 호출 가능한 형태로 감싸는 방법은 이 문서의
  범위가 아니다 — §2는 "무엇을 호출할 수 있어야 하는가"에 대한 계약(contract)만 규정한다)
