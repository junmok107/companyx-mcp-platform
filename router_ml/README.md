# 라우터 학생 분류기 (LLM 증류) — 실패한 실험 기록

> **결론 먼저: 이 접근은 실패했고, 라우터에서 제거됐다.** 아래는 무엇을 시도했고
> 왜 안 됐는지의 기록이다. 코드는 재현·참고용으로만 남긴다. 실제 라우터는
> `mcp_server/router.py`의 규칙 → LLM 2단 구조를 쓴다.

## 무엇을 하려 했나

키워드 라우터는 사전에 없는 표현을 만나면 0점을 내고 기권한다(그러면 LLM 폴백,
~2.8초). 이 "규칙 기권" 질문을 LLM 대신 빠른 모델로 처리하려고, 교사 LLM의
라우팅 판단을 경량 분류기로 증류(distillation)했다.

## 어디까지 됐나

- 임베딩(nomic-embed-text) + 분류기: 세 도구가 임베딩 공간에서 분리되지 않음
  (5-fold CV 0.60). 임베딩은 주제 유사도를 담지 임베딩 의도를 담지 못한다.
- 그래서 임베딩 대신 **의도 특징**(집계어·관계동사·문서어 카운트 등, `features.py`)
  + char n-gram으로 바꿨더니 같은 데이터에서 CV 0.94.
- 파이프라인: 교사 LLM으로 질문 생성 → 교사 재라벨링으로 노이즈 제거(374/395) →
  로지스틱 회귀 학생 학습. 추론 ~0.4ms.

## 왜 실패했나 (결정적 실험)

held-out 80문항에서는 신 3단(규칙→학생→LLM)과 구 2단(규칙→LLM)이 둘 다 0.975로
차이가 없었다. 규칙이 대부분을 커버해 학생이 개입할 일이 없었기 때문이다.

그래서 **학생이 실제로 일해야 하는 영역만** 떼어냈다 — 규칙이 기권하는(어휘 밖)
질문 15개를 엄선해 학생 vs LLM을 정면 비교했다:

| | 정확도 | 지연 |
|---|---|---|
| 학생 분류기 | **4/15 (0.27)** | 1.2ms |
| LLM 폴백 | **15/15 (1.00)** | 2,821ms |

학생이 참패했다. 원인은 분명하다: **학생의 특징(`features.py`)이 규칙과 사실상
같은 키워드 목록**이라, 규칙이 못 잡는 표현("서버가 뻗었다", "기록물을 쌓아둔다")은
학생도 못 잡았다. 겉보기엔 "의미 기반"이지만 실제로는 규칙과 같은 어휘 의존성을
물려받은 것이다. 게다가 학습 분포 밖에서는 confidence 보정도 깨져, 오답에 0.8
confidence를 주기도 했다(예: "진두지휘" → nl2sql conf=0.81, 실제 정답은 KG).

결국 3단 구조는 **LLM이 정확히 처리할 질문을 학생이 가로채 오답을 내는** 구조라
순효과가 해로웠다. 그래서 라우터에서 제거했다.

## 남는 교훈

- 로컬에서 쓸 수 있는 임베딩(nomic)은 라우팅 의도를 담지 못한다(CV 0.60, 실측).
- 키워드 특징 기반 학생은 순수 키워드 규칙과 같은 한계를 가진다 — 새 접근이 아니다.
- 이 데이터·환경에서 규칙 기권 영역을 실제로 처리하는 것은 LLM뿐이다(2.8초를 내고서라도).
- 진짜 의미 기반 라우팅을 원한다면 의도를 담는 더 강한 임베딩(더 큰 한국어 모델,
  또는 cross-encoder)이 전제이며, 그것 없이는 이 경로가 성립하지 않는다.
