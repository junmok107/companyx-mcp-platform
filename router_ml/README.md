# 라우터 학생 분류기 (LLM 증류)

키워드 라우터의 한계(사전에 없는 표현은 0점 → 판단 포기)를 보완하기 위해, 교사 LLM의
라우팅 판단을 경량 분류기로 **증류(distillation)** 한 것이다.

## 왜 임베딩이 아니라 특징 기반인가

처음엔 임베딩(nomic-embed-text) + 분류기를 시도했으나, 임베딩 공간에서 세 도구가
분리되지 않았다(5-fold CV 0.60). 임베딩은 "무엇에 관한 질문인가(주제)"는 담지만
"집계인가/관계인가/문서인가(의도)"는 담지 못한다. "직원 평균 연봉"(집계)과
"직원이 담당하는 고객"(관계)은 주제가 같아 임베딩이 가깝게 놓아버린다.

그래서 임베딩 대신 **의도를 직접 가리키는 특징**(집계어·관계동사·문서어 카운트,
엔티티 패턴 등 — `features.py`) + char n-gram(어휘 변형·오타에 강함)을 쓴다.
같은 데이터에서 이 특징으로는 CV 0.94가 나온다.

## 파이프라인 (재현 순서)

```bash
python router_ml/gen_trainset.py    # 1. 교사 LLM으로 질문 대량 생성 -> trainset.jsonl
python router_ml/gen_labels.py      # 2. 교사 LLM으로 재라벨링, 생성라벨과 불일치분 제거 -> trainset_clean.jsonl
python router_ml/train_student.py   # 3. 학생 분류기 학습 -> student_model.joblib
```

의존성: `scikit-learn`, `scipy`, `joblib` (임베딩 불필요, 학습·추론 모두 CPU).

## 라우터에서의 위치

`mcp_server/router.py`의 3단 구조에서 **LLM 폴백 앞단**에 있다:

```
규칙(0.01ms) → 학생 분류기(0.4ms, conf≥0.8일 때) → LLM 폴백(~2.8s)
```

- 규칙이 신호를 내면 학생·LLM을 부르지 않는다(가장 빠름).
- 규칙이 기권하는(사전 밖) 질문을 학생이 0.4ms에 처리한다. 학생 confidence는 잘
  보정돼 있어(≥0.8 구간 정확도 0.97 실측), 확신 없는 질문만 LLM으로 넘어간다.
- `student_model.joblib`가 없으면 학생 단계를 조용히 건너뛰고 규칙→LLM 2단으로 동작한다.

## 측정된 성능 (held-out 80문항, 학생 학습셋과 무관)

| 구성 | 정확도 | 비고 |
|---|---|---|
| 임베딩 분류기 | 0.60 | 부적합 확인 |
| 학생 분류기 단독 (LLM 없이) | 0.875 | 0.4ms |
| 규칙→LLM (구 2단) | 0.975 | |
| 규칙→학생→LLM (신 3단) | 0.975 | 이 평가셋에선 규칙 커버리지가 높아 학생 개입 적음 |

학생의 이득은 **규칙이 기권하는 질문 비중이 높은 실사용 분포**에서 나온다 —
그 질문들을 2.8초 LLM 대신 0.4ms 학생이 처리한다. 이 평가셋에서 차이가 없는 것은
평가셋이 규칙에 유리하게 구성됐기 때문이며, 한계로 명시한다.
